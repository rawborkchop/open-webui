# Implementación de OpenRouter
## Arquitectura y acceso
Fork de Open WebUI v0.12.3 en la rama `feature/openrouter-governance`. Se conservan FastAPI, Svelte y las cuentas existentes en BDD. El rol `admin` actúa como superadmin; no se ha introducido una segunda categoría de administradores limitados. Los usuarios `pending` no acceden al registro de intercambios.
El dominio de políticas vive en `backend/open_webui/openrouter`, separado de persistencia, captura de transporte y API. Una migración Alembic añade las tablas de políticas activas, revisiones, intercambios y fragmentos. Las tablas del registro no dependen del ciclo de vida del chat ni del usuario, para conservar evidencia al borrar conversaciones. SQLite funciona en el despliegue de un nodo; la migración usa tipos compatibles con PostgreSQL, pero PostgreSQL no se ha probado en este entorno.
En modo privado, los usuarios acceden únicamente a sus conversaciones, archivos, carpetas e intercambios. Compartir y los canales quedan cerrados por backend y sockets. La cuenta administradora mantiene lectura global. Los listados de recursos compartidos devuelven una colección vacía a los usuarios normales para que el frontend estándar siga funcionando. Los archivos de caché sin propietario registrado no se ofrecen a esos usuarios.
## Gobierno de parámetros
El catálogo inicial contiene parámetros de muestreo, razonamiento, herramientas, routing de proveedores, plugins, formato, entradas multimodales, Responses y embeddings. Se pueden añadir rutas nuevas desde la edición administrativa. La lista de parámetros admitidos por cada modelo se muestra cuando OpenRouter la comunica; una política no convierte en compatible un parámetro que el modelo no soporta.
Las políticas tienen ámbitos global, modelo, grupo y usuario. La autorización aplica todos los ámbitos relevantes y valida tipos, enumeraciones y límites. Los modelos con alias aplican también las restricciones del modelo base. Los valores de reglas editables son predeterminados; los de los demás modos son obligatorios. Los valores obligatorios globales prevalecen sobre los ámbitos inferiores. Los cambios usan versiones optimistas para evitar sobrescrituras y guardan historial con actor y fecha.
Los modos son editable, solo lectura, oculto y exclusivo del servidor. Las claves estructurales y credenciales no se pueden convertir en parámetros editables. La identidad `user` del proveedor siempre se calcula con el usuario autenticado. Se normalizan alias de tokens, razonamiento y parámetros JSON antes de autorizar. El servidor valida tanto el input del cliente como el payload final tras las transformaciones de WebUI. Las reglas también se aplican a las rutas directas de OpenAI compatible; el proxy genérico de OpenRouter queda cerrado.
Para usuarios normales de OpenRouter, el editor autorizado sustituye los controles genéricos de parámetros y prompt de sistema. Las expansiones de presets `model_controls` enviadas por esos usuarios se rechazan para impedir modificaciones indirectas fuera de la política; deben usar los campos autorizados.
## Captura y conservación
Se auditan las llamadas OpenRouter de chat/completions, responses y embeddings que pasan por el gateway: entrada original del cliente, cuerpo efectivo en bytes, contexto de usuario/chat/mensaje/ejecución, políticas aplicadas y fragmentos originales recibidos. Las llamadas de una misma ejecución incluyen relación con el intercambio anterior cuando comparten contexto. Se guardan hashes, tamaño, HTTP, estado, errores, ID del proveedor y proyección JSON para inspección.
Los fragmentos SSE se persisten antes de entregarlos al consumidor. Se reconstruyen contenido, razonamiento, bloques de razonamiento, herramientas y uso. La captura distingue respuesta completada, incompleta, cancelada y error. Si falla la persistencia, la inferencia no continúa silenciosamente sin registro. Los fallos de proyección opcional no descartan los bytes recibidos. Los bytes son los entregados por el cliente HTTP, después de su decodificación de transporte; no son una captura TLS ni incluyen cabeceras HTTP secretas.
Se solicita `reasoning.exclude=false`, pero solo puede conservarse el razonamiento que entregue el proveedor. Resúmenes, bloques cifrados o redactados mantienen su representación; no se reconstruye razonamiento privado. Las entradas pueden contener prompts de sistema, RAG, herramientas y datos personales y deben incluirse en las copias protegidas de BDD. No hay purga automática ni almacenamiento WORM. Los archivos binarios se conservan según el almacenamiento de WebUI; el registro guarda los cuerpos enviados y referencias de adjuntos, no descarga recursos remotos arbitrarios.
Las referencias `previous_response_id` requieren un intercambio previo del mismo usuario. Las referencias opacas de archivos/items del proveedor se rechazan para usuarios normales al no existir una asociación verificable de propietario. Los modelos fallback requieren sus permisos de acceso. Otros proveedores de Open WebUI conservan el comportamiento de upstream y no forman parte de este registro.
## API y escritorio
La API `/api/v1/openrouter` ofrece catálogo, política efectiva, políticas con historial, listados filtrables, detalle, bytes originales y exportación JSON. La propiedad se filtra en BDD; detalle, descarga y exportación ajenos devuelven 404. La entrada original en bytes solo se descarga como administrador. El detalle ordinario aplica ocultación histórica y actual; la respuesta original sigue disponible a su propietario.
La página administrativa `/admin/openrouter` y la página personal `/openrouter` se integran en el menú existente. El diseño principal de ordenador usa lista e inspector en dos columnas y tablas para revisar parámetros. Los controles del chat muestran los campos autorizados para el modelo seleccionado. El administrador puede previsualizar la política de otro usuario.
## Verificación reproducible
Con dependencias de backend y frontend instaladas:
```powershell
python -m pytest backend/tests/openrouter -q
npm run test:frontend -- --run src/lib/components/openrouter/parameters.test.ts
node --test scripts/encryption/artifact.test.mjs
npm run crypto:verify
$env:NODE_OPTIONS='--max-old-space-size=8192'
npm run build
```
La suite incluye un proceso aislado que arranca la aplicación completa, ejecuta todas sus migraciones, registra tres cuentas, activa usuarios y llama al gateway con un proveedor simulado. Comprueba aislamiento de chats, archivos, carpetas, caché, registro, exportaciones, activación/revocación de roles, políticas, respuestas JSON y SSE y razonamiento devuelto. No necesita una clave real ni usa esperas temporizadas para aprobar.
El chequeo de tipos completo de upstream presenta miles de errores ya existentes. Los componentes OpenRouter nuevos compilan sin diagnósticos propios. La compilación de producción se ha verificado en Windows; se corrigió la verificación de artefactos criptográficos para rutas con espacios y CRLF, manteniendo intactos los checksums de los binarios compilados.
Resultado final: 61 pruebas de backend, 4 de parámetros de frontend, 1 prueba de artefactos, verificación criptográfica y build de producción correctos. La compilación necesitó ampliar el límite de memoria de Node. La revisión en navegador a 1600 × 1000 no presenta errores de consola ni desbordamiento horizontal; el usuario solo ve los controles autorizados del modelo seleccionado.
Quedan fuera de la verificación de este entorno la imagen Docker, PostgreSQL, una carga de producción y la conexión autenticada real de OpenRouter. Configuración y arranque: [README](../config/openrouter/README.md). No se han usado credenciales de n8n; `OPENAI_API_KEY` permanece vacía.
